# Database Architecture & Table Explanations

The backend utilizes **PostgreSQL** (with the `pgvector` extension) accessed via **SQLAlchemy**. The schema is designed to support a robust hospital operations application, bridging physical security (Computer Vision) with clinical workflows (Audio Transcription / LLMs) and Role-Based Access Control (RBAC).

Overall, **almost all tables are actively used** by the application to power its features, with a few scaffolded for future implementations (like equipment tracking).

Below is a categorized breakdown of every table defined in `models.py`.

---

## 1. Access Control & Users (RBAC)
These tables drive authentication and authorization, ensuring users only see the dashboards and features they are allowed to.

- **`users`**: The core authentication table. Stores `username`, `hashed_password`, and a primary `role` label. 
- **`rbac_groups`**: Represents organizational roles (e.g., Doctor, Nurse, Security, Admin).
- **`rbac_permissions`**: Represents granular system capabilities (e.g., `view_camera`, `view_consultation`, `manage_staff`).
- **`user_groups`, `group_permissions`, `user_permissions`**: Junction tables mapping the Many-to-Many relationships. Users belong to Groups, and Groups hold Permissions.
> **Status**: **Highly Active**. Used extensively by `routers/auth.py` (for login/JWT) and `routers/rbac.py` (for the visual RBAC node editor in the frontend).

---

## 2. Computer Vision & Physical Security
These tables back the real-time AI processing loop that analyzes RTSP camera streams.

- **`cameras`**: Stores RTSP camera configurations, naming, physical location, and optional Home Assistant integration flags (e.g. triggering an alarm).
- **`camera_rois`**: Regions of Interest (ROIs). Stores JSON coordinate polygons drawn directly on the video feed by the user to mark distinct zones (e.g. "Restricted ICU Zone").
- **`security_alerts`**: Stores triggered alerts when an AI security rule is violated, along with severity and resolution state.
- **`security_rules`**: Stores dynamic, natural-language rules (e.g. "Doctors must wear masks in the ICU"). These are read by the Vision Language Model (VLM) during stream processing.
- **`events`** (`SystemEvent`): A generalized log table that bridges physical camera detections with the frontend timeline view.
> **Status**: **Highly Active**. This is the backbone of `services/vision_service.py` and `routers/camera_api.py`.

---

## 3. Staff Recognition & Tracking
These tables power the facial recognition and time-tracking systems.

- **`staff`**: The master record of employees. Includes `embedding` (a 512-dimension vector generated by InsightFace) for fast, vector-based face matching.
- **`staff_photos`**: Stores additional face embeddings for a single staff member (e.g. left profile, right profile) to dramatically improve recognition accuracy from different angles.
- **`attendance`**: Automatically logs the time a staff member entered the camera's view (start of shift) and when they left, alongside confidence scores.
> **Status**: **Highly Active**. Used heavily during live video inferences and by the Analytics/Attendance dashboards.

---

## 4. Clinical Data & Patients
These tables store data for the Medical Copilot workflow.

- **`patients`**: Core patient demographic information (Name, Medical Record Number, DOB, Gender).
- **`consultations`**: Records of live doctor-patient voice sessions. Stores the raw audio `transcript` generated by Whisper, and the structured `discharge_summary` generated by the LLM.
- **`medical_reports`**: Stores metadata for uploaded clinical files (e.g., X-rays, blood tests) and tracks the AI-generated key findings and abnormalities.
> **Status**: **Highly Active**. Foundational to `routers/consultation.py` and the medical agent flows.

---

## 5. Agent Memory & RAG (Retrieval-Augmented Generation)
These tables give the Medical LLM its "brain", allowing it to recall long-term facts, read hospital SOPs, and maintain chat histories.

- **`knowledge_documents` & `document_chunks`**: Stores uploaded hospital guidelines and manuals. The `chunks` table uses the `Vector` type to store semantic embeddings, allowing the LLM to perform similarity searches over large documents.
- **`conversation_history`**: A straightforward log of back-and-forth chat history between the user and the Copilot.
- **`agent_memory`**: A dynamic ChatGPT-style memory table. The agent runs a background process to extract persistent facts from conversations (e.g. "User prefers bullet points") and stores them here via embeddings.
- **`medical_faq`**: Verified Question and Answer pairs for rapid retrieval.
- **`llm_audit_log`**: Logs LLM prompts, token usage, latency, and context used. Crucial for debugging model performance and tracking API costs.
> **Status**: **Active**. Used by the `llm_manager.py` and `vector_retriever.py` pipelines.

---

## 6. Equipment Tracking
These tables are meant to track the physical location of critical hospital assets (like ventilators or wheelchairs) via camera detection.

- **`equipment_types`**: Asset definitions (e.g., Wheelchair).
- **`equipment_items`**: Specific physical instances (e.g., Wheelchair #12) and its last known location.
- **`equipment_tracking`**: A movement log tracking which camera saw which equipment at what time.
> **Status**: **Scaffolded**. The API endpoints exist in `routers/equipment.py`, but the backend YOLO loops are primarily focused on Staff/Face detection right now. This table structure is ready to be utilized once the equipment detection models are fully integrated into the vision loop.
